# PhyQGen 沟通管理计划


## 1. 沟通目标与项目背景

本计划解决三类具体协作问题：教学需求怎样转化为可验收功能；前端、后端和智能体引擎怎样使用同一套接口与状态语义；需求、模型、提示词或知识库变化后，谁需要知情、谁确认、怎样保留证据。信息送达后，应由接收者确认理解，并落实为负责人、完成条件与记录。

### 1.1 当前事实与适用边界

- 项目已有问题定义、功能规格、US-01～US-11用户故事、课标解读和算法调研；正式 `code/frontend`、`code/backend`、`code/core_engine` 仍为预留目录，`docs/software/architecture.md` 为空。
- `docs/software/prototype/frontend` 已有基于 Vue 3、TypeScript、Vite、Pinia 等技术的交互原型。页面可以演示任务、题目编辑、版本、确认、导出和管理操作；模型、检索、自动校验等为本地模拟，数据保存在浏览器 localStorage。原型可交互不代表正式系统已联通或质量已达标。
- 业务主线为：教师配置要求 → 按需检索 → 文本和配图生成 → 智能体内部校验与有限修订 → 教师人工审核、修改与确认 → 保存与TXT导出。单次生成1～5道，逐题跟踪；默认单题最多3轮，包含首次生成。
- 首轮拟邀请3～5名教师、使用不少于30道样题开展反馈和试评。这是需求中的验证目标，尚不能视为已完成招募或已得到评测结果。

### 1.2 共同使用的业务词汇

| 词汇 | 必须传达的含义 | 易产生误解的说法及处理 |
| --- | --- | --- |
| 任务完成 | 全部题处理结束，至少一份可用草稿保存成功；可同时存在失败题 | 不等于全部题成功、自动校验通过或教师确认 |
| 智能体自动校验 | 生成阶段的内部反馈，区分通过、不通过、未完成、不适用，并绑定被检查版本 | 不向教师展示内部校验意见；不能用模糊的“已审核”代替 |
| 教师人工审核与确认 | 教师直接核验、修改并明确确认具体版本 | 编辑及确认均不触发新的智能体生成或自动校验 |
| 定稿版本 | 已保存且有对应教师确认记录的版本 | 修改后成为新版本，须重新确认；旧确认不自动继承 |
| 认知目标、难度、C1～C6 | 三类不同属性；C1～C6描述题目要求的思维活动 | 不能仅凭计算复杂认定高阶，不能据题目标签直接给学生能力定级 |
| 知识库状态 | 关闭、未命中、异常应有区别，并记录普通生成的原因 | 不把未使用知识库描述为检索成功，不虚构来源 |

上述口径适用于需求、页面、接口、测试、周报和答辩。发现用词冲突，先提出关联需求的Issue，再同步修订。

## 4. 渠道、记录和信息分发

### 4.1 渠道选择

- **交互式沟通**：需求含糊、接口争议、故障定位、教师试评用短会、结对或访谈解决，结束时复述“结论、责任人、期限、验证方法”。
- **推式沟通**：阻塞、变更、发布等在团队约定即时通信群中提醒并@接收者，消息必须带对应Issue或PR链接。未确认收到时应跟进，不能把“已发送”当作理解。
- **拉式沟通**：需求、架构、管理计划、看板和测试记录用于随时查询；已决策内容统一回写仓库，避免群文件出现多个有效版本。
- **正式与非正式衔接**：私聊可用于快速讨论，涉及接口、范围、排期、质量门槛的结论应在1个工作日内补入公开于组内的记录，并请受影响负责人确认。

现有Issue #2记录了建立Kanban、Team planning和Bug tracker的任务已关闭；本次未核验Projects实际字段与访问权限。首次执行时PM检查成员与教师访问权限。若看板不可用，先以Issues的负责人、状态和里程碑维护任务，不因工具配置阻塞工作。

### 4.3 信息公开与敏感数据

本项目仓库公开，提交前检查是否含模型密钥、教师联系方式、访谈原始录音、未授权题库和私人账号数据。公开周报用教师编号代替真实姓名；原始联系方式和访谈授权保存在团队受限位置，仓库只留脱敏结论。服务工单只提供必要的脱敏请求样例、请求ID和错误码。密钥通过服务端配置或受限渠道交接，不进入Issue、截图、PR或前端代码。

### 5.2 变更流程

1. **发起**：提出者建立Issue，写清原因、对应FR/US/AC、原行为与新行为、受影响模块、工作量/排期/调用成本、验证方法和回退方案。
2. **讨论**：涉及范围和教学语义由REQ组织；接口由BE组织；模型、提示词或索引由AE组织。群内提醒受影响人员，先评审后合并破坏性变更。
3. **确认**：小范围实现改动由模块负责人和一名非作者审查；跨模块改动由所有受影响负责人确认。改变基线范围、里程碑或质量门槛须经全组评审，必要时向课程教师说明并取得要求解释。
4. **同步**：代码、文档、样例载荷和测试在同一PR或明确关联的PR中更新，记录模型/提示词/索引版本与回归结果。
5. **关闭**：接收方以复述、样例请求或回归结果证明理解；QA验证验收条件后关闭条目。若紧急故障需先止损，记录临时措施，在下一工作日补全评审及回归。

### 5.3 当前优先澄清的范围问题

- 原型保留优秀习题广场、评分和讨论。REQ须确认哪些属于US-01～US-11验收必需，哪些作为延后项；已有页面不能自动扩大本轮范围。
- 历史Issue #4提出根据答题量化科学思维；当前调研将C1～C6用于题目思维要求，不用于学生能力定级。本轮按教师命题工具边界实施，若需学生测评，另做需求、数据和评价方案评审。
- 原型README提到的外部旧项目路径、系统说明及验收记录，有部分不在当前仓库树内。BE确认可获得的迁移资产并以仓库内可复现材料为准，不把外部路径当成已交付依赖。

| 普通咨询、PR审查 | 1个工作日内确认收到；不能按期处理时说明可处理时间 | 超时由PM指定备份或调整依赖；结论回到原Issue/PR |
| 接口/需求变更 | 实现前发出，受影响者1个工作日内回应 | 未确认不得合并破坏性变更；PM协调评审时段 |
| 开发阻塞超过1个工作日 | 当日同步PM，给出已尝试方案及具体所需支持 | PM当日组织处理；再持续1个工作日或影响课程节点时，由PM向教师提出具体求助 |
| 泄露密钥、越权、定稿/导出错版、数据丢失或演示主链路阻断 | 在约定窗口内发现后立即提醒PM及BE，目标2小时内确认并指定处理人 | 先暂停受影响操作、保留证据并止损；窗口外由发现者在安全能力范围内止损，下一窗口立即响应；必要时由PM通知受影响者及教师 |
| 教学标签、物理结论或范围有争议 | 先记录双方观点、样题、课标出处与影响 | REQ组织评审；技术判断不明确时做小实验；涉及课程验收的争议请求教师确认，不以群聊投票替代证据 |

意见未决时，PM记录临时工作假设、失效日期与可逆任务。成员沉默不视为赞成，不能用“默认同意”批准范围或质量门槛变化。

## 7. 监督沟通与持续改进

PM每周利用Issue时间、PR和会议记录检查以下指标。阈值是管理预警线，不是系统质量验收指标。

| 指标 | 计算或检查方式 | 预警及处理 |
| --- | --- | --- |
| 关键信息确认率 | 已明确回复的受影响负责人次数／应确认次数 | 目标100%；缺确认的破坏性变更保持待评审 |
| 任务可追踪率 | 有唯一主责、验收条件、依赖和目标迭代的进行中任务／全部进行中任务 | 目标100%；例会补齐 |
| 超时阻塞数 | 超过1个工作日仍未升级的阻塞 | 目标0；立即指定协调人和下一检查点 |
| 跨模块返工 | 因字段、状态、版本、模型配置未同步导致的返工次数与人时 | 任一发生即复盘；连续两轮出现则调整契约评审或通知机制 |
| 风险复查完成率 | 已按计划复查的风险／当周应复查风险 | 目标100%；高优先项漏查当日补查 |
| 教师反馈处理率 | 有采纳/延后/拒绝理由及关联任务的反馈／已收集反馈 | 每轮试用结束后2个工作日内全部给出处理结论，由REQ反馈给参与教师 |

迭代回顾时只保留可执行的改进项，例如“新增带版本号的配图响应样例，并由FE在下次接入前确认”；下轮检查是否减少同类误解。人员、渠道、阶段、课程要求或架构发生变化时及时修订本计划，以PR保留历史。
