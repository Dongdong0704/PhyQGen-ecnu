# 团队计划（第 1 周起）

## 工作方式

- 所有工作从 GitHub Issue 开始：写清目标、验收标准、负责人和计划完成时间。
- 每周开始时从 Backlog 选择本周任务；每人同时进行的任务原则上不超过 2 个。
- 每周至少同步一次进展、阻碍与下一步；阻碍超过 1 天就在 Issue 留言并标记 `blocked`。
- 代码通过分支和 Pull Request 合并到 `develop`；发布候选再合并到 `main`。
- 缺陷先复现与分级，再修复、验证、关闭；复发时重开原 Issue。

## 角色与责任

| 角色 | 主要责任 | 人员 |
| --- | --- | --- |
| 产品/需求 | 访谈、范围、验收标准 | 待分配 |
| 前端 | 交互原型、页面与可用性 | 待分配 |
| 后端 | API、数据与集成 | 待分配 |
| 核心引擎 | 题目生成、校验与质量评估 | 待分配 |
| 测试/质量 | 测试场景、缺陷复现与回归 | 待分配 |

一人可以承担多个角色；每个 Issue 仍应有一位明确负责人。

## 第 1 周计划

| 任务 | 交付物 | 完成条件 |
| --- | --- | --- |
| 明确问题 | `docs/requirements/Problem_definition.md` | 团队确认 5W1H 与首批用户 |
| 明确 MVP | 首批用户故事与验收标准 | 需求 Issue 可独立实现和验收 |
| 技术方案 | 前后端与核心引擎接口草案 | 输入输出、错误和测试方式明确 |
| 流程建立 | 看板、任务和缺陷模板 | 新成员能提交并跟踪 Issue |

## 决策记录

需求和技术决策在相关 Issue 中记录结论、日期和理由；修改范围时更新 Issue 与本文件。
